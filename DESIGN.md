# Design System: EV Advisory Homepage

## Product Context
- **What this is:** A consulting homepage for EV Advisory focused on Shopify, ecommerce, conversion, and revenue-signal trust.
- **Who it's for:** Ecommerce operators, growth leads, and commerce teams who do not trust the numbers behind performance decisions.
- **Space/industry:** Ecommerce diagnostics, analytics, conversion optimization, operator consulting.
- **Project type:** Marketing site with an audit-first funnel.

## Aesthetic Direction
- **Direction:** Restrained technical editorial
- **Decoration level:** Intentional. One static grain texture is allowed, on the hero plate only (a small tiling noise image at about 4 to 5% opacity); no other textures, blur effects, or drop shadows on the plate.
- **Mood:** Clear, commercial, analytical, and operator-facing. The homepage should feel like a sharp audit memo, not a symbolic agency pitch.
- **Image rule:** No fantasy, cosmic, bird, abstract-inspiration, or vague consultancy visuals. Homepage visuals must read as diagnostics, systems, commerce, reporting, or operational clarity.

## Typography
- **Display/Hero:** General Sans
- **Body/UI:** Instrument Sans
- **Data/Labels:** JetBrains Mono
- **Scale (raised 2026-09-24; hero revised 2026-09-25; mono labels corrected 2026-09-25 CRO-6731 Pass 4):** Hero 34-64px (the headline is now two sentences, the second set at 0.56em in slate), section headings 36-72px, card headings 24-30px, stat figures 60-72px, body 18-20px, supporting copy 16-18px, mono labels 13-14px uppercase on desktop (agent name/job/tool chip 13px, step-rail labels 14px; mobile keeps its own smaller overrides). This range was documented at 12-14px since the 2026-09-24 pass, but the implementation still shipped at 11.5-12px until this fix. See the decision log entry below.
- **Real-fix (2026-09-25, CRO-6731):** the scale above was documented but not enforced. Tailwind's preflight resets `h1`-`h6` to `font-size: inherit; font-weight: inherit;` (see `assets/css/main.css` line 163 of the compiled base, sourced from Tailwind's own reset), so any heading rendered without an explicit `text-*` utility on that exact element silently inherits the surrounding body size. PR 141's reviewer measured this directly: h2 at 16px/400, identical to body, site-wide, wherever a template omitted the utility class. The fix is a base-layer fallback scale, not a rewrite of every template: add real default sizes to the existing `h1, h2, h3, h4, h5, h6 { font-family: ...; }` block in `assets/css/main.css`'s `@layer base`. Utility classes on individual elements (e.g. `home-tools.html`'s `<h2 class="text-4xl ... sm:text-6xl lg:text-7xl">`) still win because Tailwind's `@layer utilities` always outranks `@layer base` regardless of source order, so nothing already explicitly sized changes. Concrete block for the Frontend Developer to add:
  ```css
  @layer base {
    h1 { font-size: clamp(2.125rem, 1.55rem + 2.4vw, 4rem); font-weight: 700; line-height: 1.05; }       /* 34-64px */
    h2 { font-size: clamp(2.25rem, 1.4rem + 3.5vw, 4.5rem); font-weight: 700; line-height: 1.05; }        /* 36-72px */
    h3 { font-size: clamp(1.5rem, 1.35rem + 0.6vw, 1.875rem); font-weight: 700; line-height: 1.15; }      /* 24-30px */
    h4 { font-size: clamp(1.25rem, 1.15rem + 0.4vw, 1.5rem); font-weight: 600; line-height: 1.2; }        /* 20-24px */
    h5, h6 { font-size: 1.125rem; font-weight: 600; line-height: 1.3; }                                    /* 18px */
    p, li { font-size: 1.125rem; line-height: 1.7; }                                                       /* 18px body default */
  }
  ```
  This is a fallback floor, not a mandate to strip existing utility classes: templates that already set an explicit scale (hero, section headings across `home-tools.html`, `home-flow.html`, etc.) keep doing so. The block only stops a heading from silently collapsing to body size when a template forgets to size it. Reviewer check going forward: measure any new or edited heading in devtools; if it does not fall inside its documented range, the element is missing its utility class, not missing from this base block.

## Color
- **Approach:** Restrained with one strong accent
- **Ink:** `#020617`
- **Graphite:** `#0f172a`
- **Off-white surface:** `#f7f4ee`
- **Panel white:** `#f8fafc`
- **Rule/border:** `#dbe3ee`
- **Accent cyan:** `#22d3ee`
- **Accent deep:** `#0891b2`
- **Dark mode posture:** Existing site dark mode can remain, but homepage decisions should optimize for light-mode editorial clarity first, outside the dark plate band described below.
- **Colour arc (2026-09-24, supersedes the dark plate band):** the homepage is one continuous dark-to-light arc. Each section declares a tone (`data-tone`): hero Ink `#020617`, Why-work-gets-stuck `#050c1c`, How-it-works `#0b1426`, then a strong flip to Off-white `#f7f4ee` for Tools, white `#ffffff` for Proof, Off-white for Reviews and the closing CTA. `home-motion.js` blends `<main>`'s background between neighbouring tones as each boundary crosses the viewport, so it reads as one arc, never hard colour blocks. Softened 2026-09-25: each blend spans 90% of the viewport height (was 45%), starts at the same point (next section 105% down the viewport) and runs on past the boundary, on a half-linear half-smoothstep curve, so the dark-to-light flip takes about twice the scroll at well under half the peak rate. The mid-blend grey is on screen longer as a result; keep section edges padded so no small text sits in it. Without JS every section keeps its own static tone. Text colour is fixed per section (light on the dark three, Ink/slate on the light four).
- **Agent accents:** each agent has one accent used for its vehicle stripe, roof sensor, label dot and tag: Inbox cyan `#22d3ee`, CRM emerald `#34d399`, Project violet `#a78bfa`, Procurement amber `#fbbf24`, Docs blue `#60a5fa`. Finished-work states use emerald (`#6ee7b7` on the dark hero).

## Spacing
- **Base unit:** 8px
- **Density:** Comfortable but tight
- **Spacing scale:** 8 / 12 / 16 / 24 / 32 / 48 / 64 / 80

## Layout
- **Approach:** Hybrid editorial
- **Content width:** `max-w-7xl`
- **Text width:** keep most body copy at `max-w-2xl` or narrower
- **Border radius:** 16px for small surfaces, 24px for major cards, 32px for hero/CTA shells

## Motion
- **Approach (2026-09-24 highway pass):** one scroll-driven Three.js hero, a literal highway, then CSS-only motion in the process flow; minimal-functional elsewhere.
- **Highway hero (2026-09-25 hybrid, supersedes the 2026-09-24 highway pass):** a tall section (250svh desktop, 230svh phone) with a sticky 100svh stage. The road is a divided highway: two carriageways split by a low concrete median, dashed lane markings, solid edge lines, cyan road studs, guardrails, street lamps with light pools, and one concrete overpass (deck, piers, parapet, a thin cyan light line on the fascia). No signs anywhere: the old gantry and its lit sign panels are gone. Each agent vehicle runs one loop: it drives toward the viewer on the near carriageway carrying a live event tag that cycles every 2.2s (New email, CRM record added, Invoice matched, and so on), passes under the overpass where the tag turns into its finished-work state and the fascia line flashes in the vehicle's colour, leaves under the camera, then drives away on the far carriageway, taillights toward the viewer, still carrying the finished-work tag (Reply drafted, Sent for approval, Filed and linked).
- **Labels (no panels):** name and job in uppercase mono, the event tag in Instrument Sans in the agent's accent (finished work in emerald with a check), all plain type with a text shadow for legibility. A 1px stem drops from the label's baseline to the vehicle roof, ending in a small accent dot. The label slides sideways to stay on screen while the stem stays on the vehicle; nearer labels win collisions and farther ones step back. No boxed, pill or panel backgrounds on any label or tag.
- **Tool chips ("works with", 2026-09-25):** every live event tag and finished-work tag ends in a small chip after a hairline: a monochrome tool glyph plus the tool name in uppercase mono, off-white, never in brand colour and never on a panel. Each event lists the tools it can come from and each finished-work state the tools it can land in (`tools:` in `data/highway.yaml`, names in `data/brands.json`); every time an event comes round again its chip moves to the next tool, and the finished-work chip moves on once per loop. Flip timing, tag text and the done state are unchanged. Glyphs come from Simple Icons (CC0), copied into one fingerprinted sprite (`assets/icons/brands.svg`, built by `scripts/build-brand-sprite.mjs`) that only the live scene fetches, so first paint carries none of it. Brands whose owners removed their marks from Simple Icons (all Microsoft marks, AWS, Salesforce, Slack) show the name only; never draw a stand-in logo. The screen-reader description lists every tool with a no-affiliation note. The static poster does not show chips.
- **Step rail:** the four story steps are plain mono type on one hairline; the active step lights its segment. No pills.
- **Static poster:** two SVG framings (desktop and phone) projected with the scene's camera model, same no-panel labels, shown per breakpoint for first paint, no JS and reduced motion.
- **Camera:** fixed. No zoom, no push, no orbit. A level, straight-ahead camera with `setViewOffset` places the vanishing point per layout (desktop: right of the headline at 70% / 46%; phone: centred, below the copy at 50% / 70%).
- **Scroll:** progress through the pinned stage drives the four-step rail (Inputs arrive, Agents pick up, Tools get used, Work lands) and adds forward travel to the traffic. Finished-work tags are tied to position (past the overpass), not to the last scroll step. Traffic also cruises on its own, so the scene never stops.
- **Roster:** `data/highway.yaml` is the single source for the vehicles, the static poster, the process-flow rows and the screen-reader description. The agents are labelled as examples on the page.
- **Process flow ("How it works"):** a marquee of tool icons, then one row per agent: input icons, a dashed wire with a travelling packet, the agent, a second wire, and the finished output. CSS animation only. Since 2026-09-25 the rows sit between hairlines (no card per row) and the tool chips are soft pills.
- **Lazy-load and fallback:** `home-motion.js` ships unconditionally (small IIFE). The three.js scene bundle is only fetched via dynamic `import()` once the hero is within 600px of the viewport. `prefers-reduced-motion: reduce`, no `IntersectionObserver`, no JS, and failed loads all keep the inline SVG poster (same road, same agents, static labels); reduced motion also freezes the flow wires and marquee. Script URLs go through `resources.PostProcess` so they stay root-relative after `canonifyURLs`.
- **Rendering budget:** MeshStandardMaterial and additive textured planes only, no post-processing or bloom, shared vehicle geometry, instanced lane dashes, studs, posts and lamps, pixel ratio capped at 1.75 desktop and 1.25 phone, the build is staged across yielded tasks with async shader compile so no single task blocks for long, the bundle is fetched only after `load` and an idle slot, render loop stops when the hero leaves the viewport or the tab is hidden.
- **Full-page side rail, day/night cycle (2026-09-25 design pass, CRO-6731, hold from 2026-09-25 lifted):** the highway continues past the hero as a narrow fixed column instead of stopping at the pinned stage. Mockup: `docs/design/cro-6731-full-page-rail-mockup.png` (source: `docs/design/cro-6731-full-page-rail-mockup.html`).
  - **One scene, two shapes, desktop only.** The existing hero `WebGLRenderer`/`Scene`/camera is not duplicated. Once the hero's pinned stage ends, the same canvas is re-parented to a `position: fixed` host (`.hw-rail`, a sibling of `<main>`, `right: 0; top: 0; height: 100vh`) and resized from full-bleed to a fixed column: `width: clamp(220px, 22vw, 340px)`. The camera's `setViewOffset` and FOV re-tune for the narrower aspect on the same resize path already in `highway-scene.js`. No second WebGL context, no shader recompile.
  - **Content gutter.** Every `arc-section` below the hero adds `padding-inline-end: calc(var(--rail-w) + 48px)` on desktop (≥1024px) so body copy never sits under or beside the rail. `--rail-w` is a CSS custom property the rail sets on `:root` at each resize, so the gutter tracks the rail's actual width (it is not fixed at 340px on smaller desktop viewports where the `clamp()` shrinks it).
  - **Contrast.** Two independent guards, since a rail that runs the full page length behind light sections is a real WCAG AA risk the hero-only scene never had: (1) `.hw-rail` carries a CSS `mask-image: linear-gradient(to left, black 62%, transparent 100%)` on its inner (content-facing) edge, so the last ~38% of the rail's width feathers to fully transparent and `<main>`'s own arc background colour (already driving `home-motion.js`) shows through right at the point nearest body copy; (2) the scene's own materials lighten with scroll (next bullet), so by the off-white/white sections the rail's absolute luminance is already close to the page background, not just masked. Both guards apply together; neither alone is sufficient (the mask alone would still show saturated night colour bleeding from the visible 62%; brightening materials alone would still hard-edge against text at the rail's inner boundary).
  - **Mobile:** the rail is desktop-only (≥1024px). Phones keep exactly today's hero-only scene, unchanged, so the proven 84 mobile Lighthouse score is not put at risk by a second on-screen render surface on the one form factor where GPU and layout budget are tightest. The day/night story on phone stays expressed the way it already is: through `<main>`'s existing colour-arc background blend.
  - **Day/night mapping.** One new controller method on the scene, `setDayProgress(value)` (0 = hero night, 1 = at the closing CTA), fed by total document scroll fraction (not hero-local `progress`, which stays as-is for the traffic-forward-travel effect inside the hero). `setDayProgress` lerps: `scene.fog.color`, the `HemisphereLight` sky/ground colours, the `moon`/`fill` `DirectionalLight` colour and intensity (moonlight → sunlight), the road/ground albedo (`#0e1829` night → a lighter warm concrete tone by day), and a new small sun/moon disc mesh that rises along a fixed arc reusing the existing `radialTexture()` glow. Lamp posts and light pools (`buildLamps`) fade their opacity to 0 by roughly 40% day progress and are excluded from the render list past that point (not just invisible) to keep draw calls down in daylight, not because of a new geometry cap. This is the same signal already driving `home-motion.js`'s colour arc: reuse the arc's tone stops (`data-tone` per section) as the palette `setDayProgress` lerps between, so there is one authored source of truth for "what colour is this point in the page," read by two systems, instead of two authored palettes that can drift apart.
  - **Vehicles, softened.** Per EV's repeated note (card + 2026-09-25 comment) that the vehicles read as too blocky: replace the boxed sedan body/cabin (`BoxGeometry` in `sharedVehicleParts`) with a slimmer, tapered lozenge silhouette (~30% shorter vertically, no separately modelled wheels, undercarriage glow only via the existing `under` mesh), and extend the existing headlight `beamGeo`/`beamMat` pattern into a longer, more transparent trailing streak in the vehicle's accent colour. Net effect: reads as a moving light/data-packet, not a toy car, while keeping the same instancing budget (shared geometry, same material count).
  - **Render-loop gate for a fixed element.** The existing "stop when the hero leaves the viewport or the tab is hidden" contract does not transfer automatically: a `position: fixed` element is always geometrically "in the viewport," so the current `IntersectionObserver` on the hero element cannot gate the rail. The Frontend Developer must add a scroll-position sentinel (a 1px element at the very end of `<main>`, observed the same way) so the render loop stops the instant the closing CTA/footer scrolls past, and resumes if the user scrolls back up. Tab-hidden and reduced-motion gates are unchanged.
- **Fallback poster, redesigned (2026-09-25, CRO-6731):** EV called the current no-WebGL/reduced-motion fallback "crappy." It stays hero-scoped (a static image cannot scroll-track, so it does not attempt the rail) but is redrawn with: the softened light-streak vehicle silhouette above (not the boxed sedan currently in `highway-poster.html`), and a full vertical ink → dawn → off-white gradient sky (today's poster is night-only) so a user who never sees the live scroll motion still reads the "day and night" idea in one static frame. Same camera-projected framing per breakpoint, same no-panel type-on-a-stem labels, still no tool chips (unchanged rule). `home-motion.js`'s existing feature-detect gate (`!prefersReducedMotion() && canvas && sceneSrc && IntersectionObserver`) already covers reduced-motion, no-JS and no-IntersectionObserver users correctly and needs no change; `highway-scene.js` line 409's `!window.WebGLRenderingContext` check already covers no-WebGL. Both were verified present and correct in this pass.
- **Official tool logos, Outlook / Slack / Salesforce (2026-09-25, CRO-6731):** these three already rotate through the live highway chips as name-only text (`data/brands.json` carries `"glyph": null` for all three, correctly, since Simple Icons does not carry their marks; see `scripts/build-brand-sprite.mjs`'s documented policy, unchanged). EV asked for real logos where other tool logos show; for these three that place is the rotating `hw-bot__tool` chip itself (Outlook appears in 3 of the Inbox agent's events, Salesforce in 3 of the CRM agent's, Slack in 2 of the Project agent's, per `data/highway.yaml`), not a separate static row. Plan: source each mark from the vendor's own current brand-asset page (Microsoft's official Outlook product icon via its Microsoft 365/Office brand-assets download, Slack's mark via its published Media Kit / brand guidelines, Salesforce's cloud mark via its brand-assets page; exact URLs to be confirmed live at build time since none were fetched in this design pass), save the three files unmodified to a new `assets/icons/brands-official/` (kept separate from `assets/icons/brands.svg`, which stays 100% Simple Icons/CC0 as documented), and add an optional `officialLogo` field per entry in `data/brands.json` for exactly these three. `highway-scene.js`'s `setTool()` gets a third branch: `officialLogo` present → render an `<img>` at official colour in the chip; else `glyph` present → existing sprite `<use>`; else name-only (unchanged default). This is a deliberate, bounded exception to the "chips are monochrome" rule in the tool-chips entry above, scoped to exactly these three sourced, unaltered, official files, each used under that vendor's own nominative "works with" terms (no modification, no recolouring, no implied partnership or endorsement, same no-affiliation framing as the existing screen-reader note in `hero-intro.html`). Any future addition to this exception list should go through the same sourcing-and-record process, not be added ad hoc.
- **Nav:** sticky at all breakpoints. On the homepage it links only to homepage anchors (How it works, Tools, Proof, Reviews) plus the Scorecard call to action; the Services dropdown is removed for now. Other pages keep Store and Insights.
